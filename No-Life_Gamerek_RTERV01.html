1. Rendszerarchitektúra és technológiák

1.1. Négyrétegű szerveroldali felépítés

Az alkalmazást úgy terveztük meg, hogy az egyes feladatok (felhasználói kérések fogadása, üzleti szabályok ellenőrzése, adatbázis-műveletek, külső portálok elérése) élesen elkülönüljenek egymástól. Ennek köszönhetően az üzleti logika az adatbázis-kezelőtől függetlenül tesztelhető, a külső szolgáltatók pedig könnyen cserélhetők.

  • Prezentációs és API-réteg (VendeghazApp.Web): Fogadja a böngészőből érkező kéréseket és a külső fizetési szolgáltató visszajelzéseit (Webhook), ellenőrzi a jogosultságokat, majd átadja a feldolgozást az üzleti rétegnek. Itt futnak az időzített háttérfolyamatok is (iCal-szinkronizáció, lejárt zárolások törlése).
  • Alkalmazási (üzleti) réteg (VendeghazApp.Application): Megvalósítja a vendégház működési szabályait: ellenőrzi a dátumokat, kiszámítja a kuponos kedvezményeket, kezeli a 15 perces szobazárolást és összehangolja a külső naptárakat.
  • Adatelérési réteg (Repository osztályok): Elrejti a konkrét SQL és Entity Framework lekérdezéseket az üzleti réteg elől, és egységes metódusokon keresztül biztosítja az adatok mentését, módosítását és lekérdezését.
  • Adattárolási és külső integrációs réteg (VendeghazApp.Infrastructure): Tartalmazza a PostgreSQL adatbázis-kapcsolatot, az SMTP e-mail-küldőt, az iCal-elemzőt és a Stripe/Barion fizetési klienst.

1.2. Választott eszközök és indoklásuk

Terület Választott technológia Műszaki indoklás
Szerveroldali keretrendszer C# / ASP.NET Core 8 Gyors futási teljesítmény, beépített függőségbefecskendezés (Dependency Injection), egyszerűen ütemezhető háttérfeladatok (BackgroundService) és erős típusbiztonság.
Relációs adatbázis PostgreSQL 16 Megbízható tranzakciókezelés (ACID), amely elengedhetetlen a párhuzamos szobafoglalások ütközésmentes zárolásához.
ORM-adatelérés Entity Framework Core A C# osztályokból automatikusan karbantartható adatbázisséma, biztonságos, SQL-injekció ellen védett lekérdezések.
Felhasználói felület HTML5, CSS3, JavaScript (IndexedDB) Külön mobilalkalmazás telepítése nélkül fut minden böngészőben; az IndexedDB révén a takarítói felület hálózat nélkül is képes eltárolni a fényképeket és állapotokat.
Külső kapcsolatok Stripe / Barion API, iCal (.ics), SMTP Szabványos, dokumentált interfészek az online fizetéshez, a Booking.com és Airbnb naptárszinkronizációhoz és az automatikus levelezéshez.

3.2. Tranzakciós zárolás és integritás

A párhuzamos foglalások kivédésére a foglalasi_zarolas táblát használjuk. Amikor egy vendég elindítja a fizetést, az adatbázis Serializable elkülönítési (izolációs) szintű tranzakcióban ellenőrzi, hogy létezik-e bármilyen átfedő zárolás az adott szobára (zarolas.datum_tol < keresett_tavozas AND zarolas.datum_ig > keresett_erkezes). Ha nincs átfedés, azonnal beszúr egy 15 perces lejáratú sort.

3.3. Adattár- (Repository) interfészek és pontos C# metódusszignatúrák

Az adatelérési réteg öt fő Repository interfészen keresztül szolgálja ki az üzleti logikát. Az alábbiakban az összes metódus pontos szignatúrája, bemeneti paraméterei és visszatérési típusa szerepel:

1. IFoglalasRepository – Foglalások létrehozása, módosítása és lekérdezése

public interface IFoglalasRepository
{
    // Lekérdezi az adott azonosítójú foglalást a szoba, vendég, kupon és fizetés adataival együtt
    Task<Foglalas?> GetByIdAsync(int foglalasId);

    // Kilistázza a tulajdonosi naptárhoz a megadott időszak összes foglalását
    Task<IReadOnlyList<Foglalas>> GetByIdoszakAsync(DateOnly datumTol, DateOnly datumIg);

    // Új foglalást ment el FizetesreVar vagy Kifizetve (kézi rögzítés) státusszal
    Task<Foglalas> AddAsync(Foglalas ujFoglalas);

    // Módosítja egy meglévő foglalás adatait (dátum, szoba, vendéglétszám)
    Task UpdateAsync(Foglalas modositottFoglalas);

    // Státuszváltás (pl. FizetesreVar -> Kifizetve vagy Torolt) tranzakcióazonosítóval
    Task UpdateStatuszAsync(int foglalasId, FoglalasStatusz ujStatusz);

    // Visszaadja azokat a foglalásokat, amelyeknél 48 órán belül esedékes az érkezés
    Task<IReadOnlyList<Foglalas>> GetErkezesElottiErtesitendokAsync(DateOnly celDatum);
}

2. ISzobaRepository – Szabad szobák keresése és szobakezelés

public interface ISzobaRepository
{
    // Visszaadja a megadott időszakra és vendéglétszámra szabad szobák listáját
    Task<IReadOnlyList<Szoba>> GetSzabadSzobakAsync(DateOnly erkezes, DateOnly tavozas, int vendegekSzama);

    // Lekérdezi az összes szobát az adminisztrációs felülethez
    Task<IReadOnlyList<Szoba>> GetAllAsync();

    // Új szoba rögzítése vagy meglévő szoba adatainak (ár, kapacitás) frissítése
    Task SaveAsync(Szoba szoba);

    // Frissíti egy szoba takarítási állapotát (TakaritasraVar, TakaritasAlatt, Tiszta)
    Task UpdateAllapotAsync(int szobaId, SzobaAllapot ujAllapot);
}

3. INaptarRepository – Zárolások, külső iCal-naptárak és ütközések kezelése

public interface INaptarRepository
{
    // Atomi tranzakcióban ellenőrzi a szabad helyet, és létrehoz egy lejárati idővel ellátott zárolást
    Task<bool> TryIdoszakZarolasaAsync(int szobaId, DateOnly erkezes, DateOnly tavozas, TimeSpan ervenyesseg);

    // Sikeres fizetés után az ideiglenes zárolást véglegesre állítja
    Task ZarolasVeglegesiteseAsync(int foglalasId);

    // Sikertelen fizetés vagy tulajdonosi törlés esetén felszabadítja a szobát
    Task ZarolasFeloldasaAsync(int foglalasId);

    // Törli az összes lejárt ideiglenes zárolást, és visszaadja a felszabadított sorok számát
    Task<int> LejartZarolasokTorleseAsync(DateTime aktualisIdopont);

    // Lekérdezi az összes aktív külső iCal-naptárkapcsolatot
    Task<IReadOnlyList<KulsoNaptar>> GetAktivKulsoNaptarakAsync();

    // Rögzít egy észlelt foglalási ütközést az érintett foglalások azonosítóival
    Task<FoglalasiUtkozes> CreateUtkozesAsync(int szobaId, IEnumerable<int> erintettFoglalasIds);
}

4. Kivételes folyamatok és hibakezelés

Hibahelyzet Rendszerreakció és helyreállítás
Párhuzamos foglalás ugyanarra a szobára Az adatbázis-tranzakció csak az első kérést engedi át; a második vendég figyelmeztető üzenetet kap, hogy a szoba időközben foglalt lett, és visszakerül a keresőoldalra.
Félbehagyott vagy elutasított bankkártyás fizetés Sikertelen Webhook esetén a zárolás azonnal törlődik; bezárt böngésző esetén a háttérfolyamat 15 perc után automatikusan felszabadítja a szobát.
Külső iCal-szerver elérhetetlensége A szinkronizáló modul nem törli a korábban betöltött külső foglalásokat, naplózza a hibát a szinkron_naplo táblába, és a következő 5 perces ciklusban újra próbálkozik.
Egyidejű foglalás saját oldalon és külső portálon A rendszer nem törli egyik foglalást sem önkényesen: rögzíti az esetet a foglalasi_utkozes táblában, és azonnal figyelmezteti a tulajdonost a vezérlőpulton és e-mailben.
Takarítói készülék internetkapcsolat nélküli (offline) állapota A kliensoldali JavaScript a helyi IndexedDB tárolóba menti a műveletet egyedi Guid azonosítóval. Újracsatlakozáskor a szerver a ExistsByKliensMuveletIdAsync metódussal kiszűri az esetleges ismétléseket.

5. Biztonság és üzemeltetési környezet

  • Jogosultságkezelés: Az ASP.NET Core sütialapú / tokenes hitelesítése minden védett útvonalon ellenőrzi a felhasználó szerepkörét (Tulajdonos vagy Takarito).
  • Fizetési webhook védelme: A fizetési szolgáltatótól érkező értesítéseket a szerver titkos aláírókulccsal (HMAC-SHA256) ellenőrzi, így kívülről nem hamisítható sikeres fizetés.
  • Adatmentés: A PostgreSQL adatbázisról naponta egyszer automatikus biztonsági mentés (pg_dump) készül külön tárhelyre, így hardverhiba esetén is visszaállítható a foglalási naptár.
